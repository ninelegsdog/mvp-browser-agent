# ADR-002: Выбор Redis для очереди задач

## Статус
Принято

## Контекст
Для очереди задач требуется надёжное хранилище с поддержкой:
- Приоритетов очередей (high/med/low)
- Блокирующего извлечения (BLPOP)
- Мёртвых писем (DLQ)
- Повторов с задержкой
- Высокой производительности

## Рассмотренные варианты

### Вариант A: PostgreSQL (таблица очереди)
**Плюсы:**
- Уже используется в проекте для outbox
- Нет дополнительных зависимостей

**Минусы:**
- Неэффективное блокирующее извлечение (требуется polling)
- Нет встроенной поддержки приоритетов
- Более высокая задержка

### Вариант B: RabbitMQ
**Плюсы:**
- Надёжная очередь сообщений
- Поддержка приоритетов
- Мёртвые письма

**Минусы:**
- Дополнительная зависимость
- Сложность развёртывания
- Избыточен для наших нужд

### Вариант C: Redis (выбран)
**Плюсы:**
- LPUSH/BLPOP для эффективного добавления/извлечения
- Поддержка приоритетов через шардирование очередей
- Мёртвые письма через отдельный ключ
- Высокая производительность
- Уже используется в execution-layer

**Минусы:**
- Требуется отдельный сервис
- Нет встроенной транзакционной гарантии (решается через outbox)

## Решение
Используем Redis для очереди задач с приоритетами через шардирование (queue:high, queue:med, queue:low) и мёртвыми письмами (queue:dead).

## Последствия
- Требуется развёртывание Redis рядом с приложением
- Очередь не дублируется (риск потери при сбое Redis, минимизируется через мониторинг)
